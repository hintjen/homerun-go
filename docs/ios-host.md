# iOS Host

## Overview

The iOS app is a single `WKWebView` showing the shared `homerun-app-ui`
bundle. There are no native screens and there will not be any — the whole
point of the bridge is that one UI serves three hosts. This document covers
what surrounds that WebView: how the project is generated, how the bundle is
embedded and served, and how the host tells the UI what the device can do.

Three decisions here break *silently* when changed, which is why each gets a
section rather than a comment: serving over a custom scheme instead of
`file://`, injecting capabilities at document start, and generating the
project from `project.yml` rather than committing an `.xcodeproj`.

## Project generation — `ios/project.yml`

The `.xcodeproj` is generated by [XcodeGen] and gitignored. Two developers
adding files never conflict in a 4000-line pbxproj, and the build settings
stay reviewable as YAML.

```bash
npm run build:ios        # stage the UI bundle + build the Rust static library
cd ios && xcodegen generate
```

**Run `npm run build:ios` first.** `project.yml` references
`HomerunHost/web/` as a folder reference, and `xcodegen generate` fails if it
is missing. That failure is deliberate: a project that builds without the UI
produces an app with a blank screen, and a missing-directory error is far
cheaper to understand than that.

Both referenced directories are build output, staged by the npm scripts
(see [`building.md`](./building.md)):

| Directory | Contents | Staged by |
|---|---|---|
| `HomerunHost/web/` | the shared UI bundle | `npm run ui:ios` |
| `HomerunHost/lib/` | `libhomerun_pumpkin_ffi.a` (device) | `npm run rust:ios` |
| `HomerunHost/lib/sim/` | the same library for the simulator | `npm run rust:ios-sim` |

The web bundle is a **folder reference** (`type: folder`), so its contents are
copied at build time and restaging the UI does not require regenerating the
project.

### Linking the Rust library

`scripts/targets.js` stages the device and simulator slices to different
directories, so the search path is selected per SDK rather than building a fat
library:

```yaml
LIBRARY_SEARCH_PATHS[sdk=iphoneos*]:        $(SRCROOT)/HomerunHost/lib
LIBRARY_SEARCH_PATHS[sdk=iphonesimulator*]: $(SRCROOT)/HomerunHost/lib/sim
```

An `.xcframework` would also work but requires extending `build-rust.js` for
no benefit while there is exactly one consumer.

> **Load-bearing:** `OTHER_LDFLAGS` carries `-lresolv` and the `Security`,
> `SystemConfiguration`, `CoreFoundation` and `Network` frameworks. Nothing in
> the Swift sources mentions them — they are what the Rust standard library
> and its networking crates resolve against. Pruning them produces link errors
> naming symbols that appear nowhere in this repository. Learned from the
> prototype; do not rediscover it.

The library is linked from M0, before any Swift code calls it, so a toolchain
problem (missing rustup target, `crate-type` drift) surfaces immediately
rather than at M3. `AppDelegate` logs `homerun_abi_version()` in debug builds
for the same reason: a mismatch means the staged `.a` is not the one this
source was written against, which would otherwise appear much later as
nonsense decoded out of an FFI reply.

### Signing

Simulator-first: `CODE_SIGNING_ALLOWED: NO`, no `DEVELOPMENT_TEAM`, and a
placeholder bundle id of `app.gethomerun.ios`. Running on a real device — which
M3's "a friend joins over Wi-Fi" test requires — means setting a team and
turning signing back on.

## Serving the bundle — `ios/HomerunHost/AppSchemeHandler.swift`

> **Load-bearing: the bundle is served over `homerun-app://`, never
> `file://`.**

The UI is a Next.js export whose entry points are `<script>` tags fetched with
CORS semantics. A page loaded from `file://` has an **opaque origin**, those
fetches fail the CORS check, and *nothing is reported* — no console error, no
navigation failure. The symptom is a blank white screen and an empty inspector,
which is close to the least informative failure iOS can produce. A custom
scheme gives the page a real origin and the problem disappears. Capacitor and
Ionic solve it the same way.

`AppSchemeHandler` resolves a request path against `web/` in the bundle:

1. `/` becomes `/index.html`.
2. **Traversal guard**, before touching the disk: reject any path containing a
   `..` component, then require the standardized URL to still sit inside the
   root. The page chooses these URLs; two checks is not paranoia, it is one
   check for the obvious attempt and one for whatever the first missed.
3. Exact file → directory `index.html` → `path + ".html"` → `index.html`.

That third step matters because the export mixes shapes: `dashboard.html` sits
beside a `changelog/` directory, so one route can arrive as any of three
spellings. The final fallback is what lets a client-side route survive a
reload.

**A missing path *with* an extension returns 404, not `index.html`.** Serving
HTML in place of a missing JavaScript chunk fails deep inside the parser, where
the real cause — a file that is not there — is invisible.

MIME types come from an explicit table rather than `UTType`, which maps `.js`
to `application/javascript`; WebKit refuses to execute that as a module. This
is the same blank-screen failure as the `file://` trap, arriving by a different
route.

## Capability injection — `ios/HomerunHost/Capabilities.swift`

The UI resolves capabilities **synchronously as its first act** and cannot
await the host (PROTOCOL.md §4.1). They are therefore injected as a
`WKUserScript` at `.atDocumentStart`:

```swift
window.__homerunCapabilities = { "platform": "ios", ... };
```

The object is read out of the vendored `shared/conformance/bridge-v1.json`
(`profiles.ios.capabilities`), which ships as a bundle resource — **not**
transcribed into Swift. The contract is generated from the UI repo and
re-vendored by `scripts/sync-contract.js`; a hand-copied copy would silently
fall behind it. **Every field must be present: a missing one is a host bug, not
a default the UI fills in.** Reading it from the manifest makes that true by
construction.

Failure to load it is `fatalError`, deliberately. A host that boots without
capabilities renders a UI making wrong assumptions about the device, which is
much harder to diagnose than a crash at launch.

For iOS the profile declares `serverBackends: ["pumpkin"]`,
`deviceWebsocket: true`, and everything else false — notably
`moddedServers: false` (Pumpkin runs no Bukkit plugin or Fabric mod) and
`backgroundExecution: false` (iOS cannot host in the background).

## App shell — `AppDelegate.swift`, `MainViewController.swift`

UIKit, window-based, **no scenes and no SwiftUI**. The app is one WebView for
its whole life, and that view's configuration — scheme handler, user scripts,
message handler — must be fixed before the view is created. A SwiftUI
`UIViewRepresentable` would put a diffing lifecycle in front of a view that
never changes, for no benefit. The hooks later milestones need (deep links,
save-on-suspend, the idle timer) also live naturally on the app delegate.

The WebView is pinned to the view's edges, **not** its safe area: the UI
handles insets in CSS with `env(safe-area-inset-*)`, so letting UIKit inset it
as well double-counts the notch. Rubber-banding and automatic content insets
are off for the same reason.

### Launch colour

Three surfaces have to agree or launch flashes, and they are configured in
three different places:

| Surface | Set in | When it shows |
|---|---|---|
| Launch screen | `Info.plist` → `UILaunchScreen` → `UIColorName` | Before any code runs |
| Window | `MainViewController.viewDidLoad` | Between the launch screen and the first paint |
| WebView backing | `BridgeController.init` (`isOpaque = false` + `backgroundColor`) | Any moment the page has not painted |

All three are `Brand.launchBackground` — `#5677DA`, the colour the bundle's
splash animation sits on. The launch screen can only be given a colour from an
asset catalog, so the value lives in
`Assets.xcassets/LaunchBackground.colorset` and `Brand` reads it back out with
`UIColor(named:)` rather than repeating the hex in Swift.

White was the previous answer to all three, and it was visibly wrong twice: as
a flash before the splash, and as a white frame behind every reload on a dark
device — where the system launch background was black on top of that.

### Status bar

`preferredStatusBarStyle` follows **the page**, not the device. The two
disagree routinely: the UI is next-themes with `defaultTheme: "system"`, and a
player who pins light or dark gets a page that contradicts
`traitCollection.userInterfaceStyle`. Hard-coding `.darkContent` — which this
did — leaves a black clock and battery on a black page.

The page says so on the **`set-appearance`** channel (`light` or `dark`), which
the router hands to `BridgeController.appearanceChanged` through
`BridgeEventSink`. The web layer cannot do this itself: in a WKWebView the
clock and battery are drawn by the view controller, and
`apple-mobile-web-app-status-bar-style` applies only to a home-screen web app.

> Briefly, before the channel existed, this host inferred the theme from a
> document-start script watching the class next-themes puts on `<html>`. The
> contract replaced it and the script was deleted rather than kept as a
> fallback: the embedded bundle is the floor for over-the-air delivery, so
> there is no bundle old enough to need it. `WKWebView.themeColor` is a third
> way to read the same thing — the UI publishes `theme-color` — if the channel
> ever needs a backstop.

`BridgeController.pageTheme` goes back to nil only when the **content process
dies**, because that is the one case where what is on screen becomes the launch
blue. An ordinary navigation keeps it: WebKit leaves the old page up until the
new one paints, so clearing it there would flash a white clock over a light
page for as long as the load takes.

## File map

| File | Role |
|---|---|
| `ios/project.yml` | XcodeGen definition: sources, linking, signing, Info.plist |
| `ios/HomerunHost/Info.plist` | Bundle metadata, `homerun://` URL scheme, no background modes |
| `ios/HomerunHost/HomerunHost.entitlements` | Empty until there is a team; associated domains land at M2 |
| `ios/HomerunHost/AppDelegate.swift` | `@main`, window, owns the bridge |
| `ios/HomerunHost/MainViewController.swift` | Full-screen WebView layout, status bar style |
| `ios/HomerunHost/Brand.swift` | The launch colour, read from the asset catalog |
| `ios/HomerunHost/Assets.xcassets` | `LaunchBackground` — the one colour `UILaunchScreen` names |
| `ios/HomerunHost/AppSchemeHandler.swift` | Serves `web/` over `homerun-app://` |
| `ios/HomerunHost/Capabilities.swift` | Reads `profiles.ios.capabilities`, builds the document-start script |
| `ios/HomerunHost/FFI/HomerunFFI.h` | Hand-written C header for the Rust library |

## Triage

**Blank white screen, empty console.** The bundle is being served over
`file://`, or a `.js` file went out with the wrong MIME type. Both make module
scripts fail with no error. Check that `AppSchemeHandler` is registered on the
configuration *before* the WebView is constructed, and that the MIME table maps
`js` to `text/javascript`.

**The clock and battery are invisible against the page.** The status bar style
is stale. It is driven by the `set-appearance` channel, so either the page
never sent one — check `npm run conformance:ios`, and look for
`cannot do that yet (set-appearance)` in the log, which is what an unregistered
handler looks like — or `MainViewController` lost the `bridge.onThemeChanged`
hook that calls `setNeedsStatusBarAppearanceUpdate()`. Nothing polls; a missed
send stays missed until the theme changes again.

**A white flash before the splash.** One of the three launch surfaces is not
`Brand.launchBackground` — see the launch colour table. A flash *only* at cold
start is the launch screen: `UIColorName` is only honoured when the named
colour exists in an asset catalog that actually ships, and a typo fails silently
back to the system background.

**`xcodegen generate` fails on a missing path.** `HomerunHost/web/` is not
staged. Run `npm run build:ios`.

**App launches to a white screen, inspector shows 404s for `_next/...`.** The
web folder reference is in the project but empty, or was staged after the last
build. Restage and rebuild.

**`readInjectedCapabilities: window.__homerunCapabilities is missing`.** The
user script is not being injected at document start, or `bridge-v1.json` is not
in the bundle. Confirm the resource is listed in `project.yml`.

**Crash at launch, "bridge-v1.json is missing".** Same cause as above, caught
on the native side first.

**Link fails on `_res_9_init`, `SecRandomCopyBytes`, or similar.**
`OTHER_LDFLAGS` lost `-lresolv` or one of the frameworks. See the linking
section — no Swift source references these.

**"You have not agreed to the Xcode license agreements."** Run
`sudo xcodebuild -license accept`. This blocks both `xcodebuild` and any cargo
build that shells out to `cc`.

**Xcode builds but the tools do not.** `xcode-select -p` points at
`/Library/Developer/CommandLineTools`. Point it at the app:
`sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.
